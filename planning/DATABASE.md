# Database Layer — Interface Contract

The SQLite layer lives in `backend/app/db/`. No module outside that package writes SQL.
This document is the contract: signatures, return types, and error behavior other agents code against.

## Quick Start

```python
from app.db import initialize_database, transaction
from app.db.repositories import chat, positions, profile, snapshots, trades, watchlist

initialize_database()                 # Once, at app startup. Idempotent.

cash = profile.get_cash_balance()     # 10000.0 on a fresh database
tickers = watchlist.list_tickers()    # ['AAPL', 'GOOGL', ...]
```

## Rules of Engagement

- **All functions are synchronous.** FastAPI handlers must call them via `asyncio.to_thread(...)`.
  Background tasks that are already in a thread can call them directly.
- **Every function returns dataclasses or plain values**, never `sqlite3.Row`. Each dataclass is
  frozen and has `to_dict()` for JSON responses.
- **Every function accepts `user_id: str = "default"` as its last-but-one argument** and
  `conn: sqlite3.Connection | None = None` as its last. Pass `conn` to join a transaction
  (see below); omit it and the call commits on its own.
- **Tickers are normalized** (stripped, uppercased) on write and on lookup. `"aapl"` and `"AAPL"`
  are the same row.
- **Timestamps are ISO 8601 UTC strings** with microseconds, e.g. `2026-07-26T14:03:11.482913+00:00`.
  They sort lexicographically, so string comparison is valid for ordering and filtering.
- **IDs are UUID4 strings** generated by this layer. Never supply your own.
- **No business validation.** The layer stores what it is told: cash can go negative, quantities
  can be anything. Affordability and share-count checks belong to the portfolio service.

## Configuration

| Name | Value |
|---|---|
| `FINALLY_DB_PATH` (env) | Overrides the database file location. Read on every connection. |
| Default path | `<project root>/db/finally.db` |
| Docker | Set `FINALLY_DB_PATH=/app/db/finally.db` (the volume mount). |

Constants exported from `app.db`: `DEFAULT_USER_ID = "default"`, `DEFAULT_CASH_BALANCE = 10000.0`,
`DEFAULT_TICKERS` (the 10 seed tickers, a tuple).

## Initialization

```python
initialize_database(path: Path | None = None) -> None
```

Creates all six tables plus indexes and seeds the default profile (cash 10000.0) and the 10 default
tickers. Fully idempotent — existing data is never overwritten. Parent directories are created.

Initialization is also **lazy**: the first repository call on a given database file runs it
automatically. Calling `initialize_database()` at startup is still recommended so failures surface
early.

The connection has `journal_mode=WAL` and `foreign_keys=ON`. Each call opens and closes its own
connection, so the layer is safe to use from multiple threads.

## Transactions

Group several writes atomically by opening one connection and threading it through:

```python
from app.db import transaction

with transaction() as conn:
    profile.adjust_cash_balance(-1900.0, conn=conn)
    positions.upsert_position("AAPL", 10.0, 190.0, conn=conn)
    trades.record_trade("AAPL", "buy", 10.0, 190.0, conn=conn)
```

Commits on clean exit, rolls back on any exception. Reads inside the block see the block's own
uncommitted writes. Without `conn`, every call is its own transaction.

## Dataclasses

All are `@dataclass(frozen=True, slots=True)` with a `to_dict()` method.

| Class | Fields |
|---|---|
| `UserProfile` | `id`, `cash_balance: float`, `created_at: str` |
| `WatchlistEntry` | `id`, `user_id`, `ticker`, `added_at` |
| `Position` | `id`, `user_id`, `ticker`, `quantity: float`, `avg_cost: float`, `updated_at`; property `cost_basis` (`quantity * avg_cost`, rounded to 2) |
| `Trade` | `id`, `user_id`, `ticker`, `side: "buy" \| "sell"`, `quantity: float`, `price: float`, `executed_at`; property `notional` (`quantity * price`, rounded to 2) |
| `PortfolioSnapshot` | `id`, `user_id`, `total_value: float`, `recorded_at` |
| `ChatMessage` | `id`, `user_id`, `role: "user" \| "assistant"`, `content: str`, `actions: dict \| None`, `created_at` |

`Position.to_dict()` adds `cost_basis`; `Trade.to_dict()` adds `notional`.

## `repositories.profile`

```python
get_profile(user_id="default", conn=None) -> UserProfile
get_cash_balance(user_id="default", conn=None) -> float
set_cash_balance(balance: float, user_id="default", conn=None) -> UserProfile
adjust_cash_balance(delta: float, user_id="default", conn=None) -> UserProfile
```

- `get_profile` raises `ValueError` if the user id has no row. The `"default"` user always exists
  after initialization.
- `set_cash_balance` writes an absolute value; `adjust_cash_balance` applies a delta in a single
  SQL statement (negative to spend). Neither prevents a negative balance.
- Both mutators return the updated profile.

## `repositories.watchlist`

```python
list_watchlist(user_id="default", conn=None) -> list[WatchlistEntry]
list_tickers(user_id="default", conn=None) -> list[str]
get_entry(ticker: str, user_id="default", conn=None) -> WatchlistEntry | None
has_ticker(ticker: str, user_id="default", conn=None) -> bool
add_ticker(ticker: str, user_id="default", conn=None) -> WatchlistEntry
remove_ticker(ticker: str, user_id="default", conn=None) -> bool
```

- Listings are ordered by `added_at`, then ticker.
- `add_ticker` is **idempotent**: adding a ticker already on the watchlist returns the existing
  entry unchanged and never raises. Use `has_ticker` first if the caller needs to report
  "already watching".
- `remove_ticker` returns `True` if a row was deleted, `False` if the ticker was not watched.
  It never raises for an unknown ticker.
- The layer does not validate that a ticker symbol exists in the real world.

## `repositories.positions`

```python
list_positions(user_id="default", conn=None) -> list[Position]
get_position(ticker: str, user_id="default", conn=None) -> Position | None
upsert_position(ticker: str, quantity: float, avg_cost: float, user_id="default", conn=None) -> Position
delete_position(ticker: str, user_id="default", conn=None) -> bool
```

- `list_positions` is alphabetical by ticker. A user with no holdings gets `[]`.
- `upsert_position` takes **absolute** values, not deltas: the caller computes the new quantity and
  the new weighted-average cost. It creates the row or overwrites quantity/avg_cost, keeping the
  original `id`, and refreshes `updated_at`.
- A fully sold position should be removed with `delete_position` rather than left at quantity 0.
  `delete_position` returns `False` when there was nothing to delete.
- Fractional quantities are supported.

## `repositories.trades`

```python
record_trade(ticker: str, side: str, quantity: float, price: float, user_id="default", conn=None) -> Trade
list_trades(ticker: str | None = None, limit: int | None = None, user_id="default", conn=None) -> list[Trade]
```

- The table is append-only; there is no update or delete.
- `record_trade` raises `ValueError` if `side` is not `"buy"` or `"sell"`. It stamps
  `executed_at` itself and returns the stored `Trade`.
- `list_trades` returns **most recent first**, optionally filtered by ticker and capped by `limit`.

## `repositories.snapshots`

```python
record_snapshot(total_value: float, user_id="default", conn=None) -> PortfolioSnapshot
list_snapshots(since: str | None = None, limit: int | None = None, user_id="default", conn=None) -> list[PortfolioSnapshot]
latest_snapshot(user_id="default", conn=None) -> PortfolioSnapshot | None
```

- `record_snapshot` stamps `recorded_at` with the current UTC time. Call it every 30 seconds from
  the background task and immediately after each trade.
- `list_snapshots` returns **chronological order (oldest first)** — plot-ready. `since` is an
  inclusive ISO timestamp lower bound. With `limit`, the most recent `limit` rows are returned,
  still oldest-first.
- `latest_snapshot` returns `None` when nothing has been recorded yet.

## `repositories.chat`

```python
add_message(role: str, content: str, actions: dict | None = None, user_id="default", conn=None) -> ChatMessage
list_messages(limit: int | None = None, user_id="default", conn=None) -> list[ChatMessage]
clear_messages(user_id="default", conn=None) -> int
```

- `add_message` raises `ValueError` if `role` is not `"user"` or `"assistant"`. There is no
  `"system"` role in storage — the system prompt is built at call time.
- `actions` must be a JSON-serializable **dict**; it is stored as JSON text and returned parsed.
  Use `None` for user messages. Suggested shape for assistant turns:
  `{"trades": [...], "watchlist_changes": [...], "errors": [...]}`.
- `list_messages` returns **chronological order (oldest first)**, which is the order an LLM prompt
  needs. With `limit`, the most recent `limit` messages are returned, still oldest-first.
- `clear_messages` returns the number of rows deleted.

## Error Behavior Summary

| Situation | Behavior |
|---|---|
| Unknown `user_id` in `get_profile` | `ValueError` |
| Invalid trade `side` | `ValueError` |
| Invalid chat `role` | `ValueError` |
| Adding a duplicate watchlist ticker | No error; returns the existing entry |
| Removing an absent watchlist ticker / position | No error; returns `False` |
| Reading an absent position, entry, or snapshot | Returns `None` |
| Reading an empty table | Returns `[]` |
| Exception inside `transaction()` | Rolled back, then re-raised |

## Schema Reference

Six tables, exactly as specified in `PLAN.md` section 7. Every table has `user_id` defaulting to
`'default'`. `watchlist` and `positions` carry `UNIQUE (user_id, ticker)`. `trades.side` and
`chat_messages.role` are `CHECK`-constrained. Indexes exist on `(user_id, executed_at)`,
`(user_id, recorded_at)`, and `(user_id, created_at)` for the history queries.
